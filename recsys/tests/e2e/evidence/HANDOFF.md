# Передача 03-EVIDENCE

## Локальный запуск

Из каталога `recsys` выполните в PowerShell:

```powershell
$fixture = 'internal/enrichment/testdata'
go run -mod=readonly ./cmd/enrich -feed "$fixture/mini-feed.xml" -items "$fixture/mini-items.json" -sources "$fixture/mini-sources.json" -feed-url https://example.com/demo-feed.xml -catalog-version mini-v1 -snapshot demo-v1 -cutoff 2026-08-31T23:59:59+05:00 -card DEMO-RENEW-12
go test -mod=readonly -count=1 -v ./internal/enrichment/... ./internal/explain/...
```

Команда читает XML или gzip по сигнатуре. URL указывает происхождение, чтение идёт из локального файла. Зафиксируйте одну неизменяемую версию на входной фид и используйте его временную зону для YML без смещения. CLI принимает отсечение как точный момент RFC3339. В примере `post_cutoff: true`, поскольку фид и правило получены после отсечения. `available` относится к версии фида. У третьего оффера оно явно `false`, а у оффера 504 неизвестно.

Вход правила `demo-renewal` задаёт `DEMO-BASE → DEMO-RENEW-12` и точную цитату. Проверенная запись в `mini-sources.json` фиксирует направление и ограничения на 10–14 узлов у обоих товаров и срок 12 месяцев у цели. Результат содержит одно ребро `renewal` со снимком `demo-v1`, ссылку на источник `demo-rules-v1` и проверенные ограничения. Фикстура сравнивает Base, Renewal на 12 месяцев и Renewal на 24 месяца. У обоих сроков свои ID и источники. Второе правило попадает в `rejected`: заявленной цитаты про продление на 24 месяца в документе нет. При повторной обработке и перестановке офферов результат совпадает.

Офферы 504 и 505 имеют одинаковый SKU, поэтому оба попадают в `candidates` со статусом `ambiguous`. Точное имя без SKU и предложения поискового порта требуют проверки. Сопоставление проверяет сначала `vendorCode`, затем артикул из URL. Из последнего сегмента URL сначала удаляется конечный числовой ID оффера вместе с предшествующим дефисом. Одно правило для артикула из продаж, `vendorCode` и артикула из URL переводит буквы в верхний регистр и оставляет только буквы и цифры, включая ведущие нули. Если один ключ в выбранном способе поиска соответствует нескольким офферам, результат содержит всех кандидатов со статусом `ambiguous`. При двух разных item ID, претендующих на один оффер, оба результата помечаются неоднозначными. Перед применением к v4 проверьте эти решения на схеме реального фида.

YML-параметры «Совместимая архитектура/платформа» и «Срок действия» пишутся в `platform` и `term` с теми же единицами измерения и источниками, что и прежние имена. Пустые значения остаются неизвестными, конфликт значений или единиц вызывает ошибку.

## Подключение

- `enrichment.ReadFeed` потоково передаёт офферы посетителю. Публикуйте выход после успешного завершения чтения. CLI накапливает один снимок для повторного поиска и вывода JSON.
- `enrichment.Build` принимает фид, ID снимка рекомендаций, отсечение, офферы, товары и рецензированные записи. `Document.Text` — сохранённый текст источника. Проверяющий фиксирует семантику и ограничения в `ReviewedStatement`. Модуль сверяет цитату, направление и соответствие ограничениям фида. Допуск исходных документов и ручная проверка смысла выполняются до вызова `Build`.
- `enrichment.Searcher.Search(ctx, catalogVersion, query, limit)` — порт участника 4. Поиск должен возвращать офферы переданной версии и основание для каждого результата. В приложении точные индексы уже строятся в памяти. В PostgreSQL `pg_trgm` и `vector` пригодятся для подбора кандидатов к проверке. Расширения, индексы и подключение адаптера принадлежат участнику 4.
- Для SQL-публикации нужна транзакционная запись версии фида, офферов, статусов сопоставления и источников. Сохраните старые версии и стабильные ID для существующих FK. Один из вариантов — отдельные таблицы с ключом `(catalog_version, offer_id)` и выбор соответствия в пределах версии. Одинаковая партия должна повторно публиковаться идемпотентно. Для чтения по снимку нужны семья с источником, ограничения, подтверждённые связи и признаки/варианты.
- Участник 2 потребляет `Relations`, `Families` и `Variants`, выставляет `evidence_ids` для выбранных рёбер, добавляет узлы в `Graph` и собирает `domain.Recommendation`. `explain.Render` принимает уже отобранные для карточки факты. Участник 1 получает `Families` для разбивки метрик и фиксирует версии. Для сравнения с baseline используйте только товары продаж v4. Онлайн-допуск по наличию применяется к конкретной версии каталога.

## Провайдеры и кеш

`explain.ChatFromEnv` и `explain.EmbeddingsFromEnv` читают переменные `LLM_*` и `EMBED_*` процесса. BASE_URL должен быть корнем API, например с префиксом `/v1`. Адаптеры используют JSON-методы `/chat/completions` и `/embeddings`, таймаут 15 секунд на запрос и поддерживают отмену через контекст. Базовый сценарий CLI всегда локальный. Для чата можно явно добавить `-public-text <файл>` с полями `text`, `source_url`, `version`, `approved`. Передавайте только подтверждённый к отправке публичный текст. Чат выбирает порядок подтверждённых фраз. Ошибка, таймаут или ответ вне разрешённых значений дают шаблон с `provider: "template"`.

Ключ для сохранения эмбеддингов между процессами — идентификатор API, неизменяемая версия модели, размерность и SHA-256 точного текста. Метаданные источника храните рядом. Внутри экземпляра адаптера уже есть кеш по хешу, модель фиксируется конфигурацией, а размерность проверяется между батчами. Повторный вызов после сбоя переиспользует завершённые батчи. Долговременный кеш принадлежит интеграции с хранилищем. Для сохранения выбора чата используйте идентификатор API, версию модели и промпта и SHA-256 публичного фрагмента.

Без внешней сети воспроизводятся мини-фид, сопоставление, проверка источника, сравнение вариантов, шаблон и все тесты провайдеров через локальный `httptest`. [Публичный факт для питча](../../../internal/enrichment/testdata/public-microsoft-365.md) проверен отдельно по первоисточнику.
